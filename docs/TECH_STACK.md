# 技术栈方案（V3 / MVP · APK）

- 对应文档：`docs/PRD.md`
- 日期：2026-10-23
- 版本沿革：
  - V1 微信小程序 + 云开发 —— **作废**（改为 APK 后云开发不可用）
  - V2 APK + Node/Fastify + PostgreSQL —— **作废**（后端正为 FastAPI、库改为 MySQL）
  - **V3 APK + FastAPI + MySQL 8.0 + 邮箱验证码 —— 当前方案**
- 原则：能不加的组件一律不加；组件数量本身就是维护成本

---

## 1. 本次变更（V2 → V3）

| 项 | V2 | V3 | 连带影响 |
| --- | --- | --- | --- |
| 后端 | Node.js + Fastify | **Python 3.12 + FastAPI** | 依赖全部换 Python 生态 |
| 数据库 | PostgreSQL 16 | **MySQL 8.0** | 并发写法要改（见 5.1、5.2） |
| 登录介质 | 手机号 + 短信验证码 | **邮箱 + 邮件验证码** | 免短信签名审核，但引入投递风险 |

三处变更带来的净影响：

- ✅ **省掉短信签名与模板审核**（原需 1–3 个工作日），也没有按条计费。
- ✅ **FastAPI 自动生成接口文档**，前后端联调不用手写 API 文档。
- ⚠️ **MySQL 没有 `RETURNING`**，名额并发要换写法；另有一个会导致超约的驱动参数坑（5.2）。
- ⚠️ **邮件到达率不可控**，比短信更容易卡在"收不到验证码"上（第 4 节）。

## 2. 结论

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 客户端 | uni-app（Vue 3 + Vite） | 一套代码可出 APK / H5 |
| 后端 | Python 3.12 + FastAPI | 单体，单进程多 worker |
| ASGI 服务 | uvicorn（容器内 2–4 worker） | 不用 gunicorn 套一层 |
| ORM | SQLAlchemy 2.0（async）+ Alembic | 迁移管理 |
| 驱动 | asyncmy | 备选 aiomysql |
| 数据校验 | Pydantic v2 | FastAPI 内置，不用额外引 |
| 数据库 | MySQL 8.0（InnoDB / utf8mb4） | 必须 8.0，不用 5.7 |
| 认证 | JWT（PyJWT） | 30 天有效期 |
| 邮件 | aiosmtplib（SMTP 直发） | 学校邮箱 / 企业邮 / 邮件推送 |

| 反向代理 | Caddy | 自动申请并续期 HTTPS |
| 运行 | Docker Compose（caddy / app / mysql） | **三个容器，不加第四个** |

## 3. 选型理由

### 3.1 为什么 FastAPI 适合这个项目

1. **自动 OpenAPI 文档**（`/docs`）。本项目有十几个接口要前后端联调，FastAPI 让接口文档永远和代码同步，省掉"文档过期导致联调返工"这一类问题。
2. **Pydantic 校验是刚需**。预约提交、结果录入、号源配置都是表单型接口，字段校验和错误提示占了不小工作量，FastAPI 内置掉了。
3. **异步发邮件不阻塞**。SMTP 握手常见 1–3 秒，async 天然适配。
4. **Excel / 二维码 / 邮件** 三个周边能力在 Python 生态都很成熟（openpyxl、qrcode、aiosmtplib）。
5. 代价只是需要一个 Python 运行时——用 Docker 封装后，运维侧无感知。

### 3.2 为什么 MySQL 8.0 而不是 5.7

必须 8.0：utf8mb4 默认字符集、更好的索引与 JSON 支持、CTE。5.7 在中文与 emoji 上要额外配，没有收益。

**名额并发依然一条 SQL 解决**，不需要锁也不需要 Redis（见 5.1），这是 MySQL 在本项目里最关键的适配点。

### 3.3 邮箱验证码的取舍

| | 短信 | 邮箱 |
| --- | --- | --- |
| 签名/模板审核 | 需 1–3 天 | **不需要** |
| 单条成本 | 分位级/条 | **0（学校 SMTP）** |
| 到达率 | 高 | **取决于 SPF/DKIM 配置，可能进垃圾箱** |
| 用户习惯 | 人人会用 | **学生可能不常查邮箱** |
| 唯一性 | 手机号强绑定 | 邮箱可随意填、可共用 |

技术上完全可行，**但它是本方案里最需要提前验证的一环**——见第 4 节。

## 4. 邮箱验证码：落地细节与风险

### 4.1 发信通道（按推荐顺序）

1. **学校邮箱 SMTP**（如 `@hebau.edu.cn`）。发信域名自带信誉，最不容易被判垃圾邮件，通常免费。
   ⚠️ 需先确认：是否允许程序化外发、有无日发送限额、是否限制校外 IP 连接。
2. **腾讯企业邮 / 阿里云邮件推送**。需验证发信域名并配置 SPF/DKIM，有免费额度。
3. **自建 Postfix**。不推荐：IP 信誉差、维护成本高、极易进垃圾箱。

### 4.2 必须做的三件事

- **配 SPF / DKIM / DMARC**。不配基本必进垃圾箱，这是硬门槛，不是优化项。
- **正文写清楚**：发信人显示名为「河北农业大学校医院」，正文含验证码、有效期、"非本人操作请忽略"。
- **频控**：同一邮箱 60 秒一次、同一邮箱每日上限、同 IP 上限。验证码 10 分钟有效、一次性、用后立即失效。

### 4.3 验证码存 MySQL，不存内存

uvicorn 多 worker 是独立进程，内存不共享——**用进程内 dict 存验证码，在多 worker 下会随机失效**，这是最容易踩的坑。

落一张小表即可：

```
email_code(email, code_hash, expires_at, used, created_at)
索引：(email, created_at)
```

定时任务清理过期行。**这也是本项目不需要 Redis 的直接原因。**

### 4.4 发信不能阻塞接口

用 FastAPI `BackgroundTasks`：接口立刻返回"验证码已发送"，发信在响应之后执行。失败重试 2 次并记日志。**不需要消息队列。**

### 4.5 风险清单（需甲方确认）

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 学生是否人人有可用邮箱 | 尤其是否统一使用学校邮箱；用 QQ 邮箱则无法与学号对应 | 需确认，见 PRD Q17 |
| 登录转化率下降 | 学生要找邮箱、等信、翻垃圾箱，中途放弃概率高于短信 | 页面提示"未收到请检查垃圾邮件"；提供重发 |
| 校内邮箱限制外发 | 部分学校邮箱禁止程序外发或限 IP | 开工前用脚本实测一次 |
| 邮箱可随意填写 | 邮箱不天然等于"某个学生" | 身份仍靠学号+姓名绑定（PRD S2），邮箱只是登录凭据 |

> **唯一建议的预留**：把发信抽象成一个 `Notifier` 接口（`send_code(email, code)`），先实现邮件版。若投递率不达标要退回短信，只换实现类、不动业务代码。这不算新增组件。

## 5. MySQL 适配要点

### 5.1 名额并发：一条 UPDATE（验收 5.2 第 5、7 条）

```sql
UPDATE time_slot
SET booked_count = booked_count + 1
WHERE id = %s AND booked_count < capacity;
```

`cursor.rowcount == 1` 即抢到，`0` 即满额。InnoDB 行锁保证并发下不超约、不出现负余量。

防重复预约靠唯一约束，不靠查表：

```sql
UNIQUE (student_id, session_id)
```

插入冲突（MySQL 错误码 **1062**）即判定"已预约过"，捕获后回滚整个事务。流程：扣名额 → 插预约单 → 任一步失败则回滚。

### 5.2 两个必须知道的坑

1. **MySQL 没有 `RETURNING`**。想拿扣减后的余量不能像 PostgreSQL 那样一次返回，要么再查一次，要么 `SELECT ... FOR UPDATE` 先锁再算。**建议只判断 rowcount，不依赖返回值**，最省事也最不容易错。
2. **绝对不能开 `CLIENT_FOUND_ROWS`**。开启后 `affected_rows` 返回的是"匹配行数"而非"实际改变行数"，**满额时也会返回 1，直接导致超约**。SQLAlchemy 默认不开启，但连接串参数或某些驱动配置会打开，**必须显式确认连接参数**。这条一旦踩中，验收 5.2 第 5 条必挂，且线上表现为"号满了还能约"。

### 5.3 其他约定

- 字符集 `utf8mb4` / 排序规则 `utf8mb4_0900_ai_ci`。
- **时区统一存 UTC**，接口返回带时区的 ISO8601，前端本地化。不统一会出现"约的 8 点显示成 0 点"。
- 索引：`time_slot(session_id, slot_start)`、`appointment` 唯一键 `(student_id, session_id)`、`appointment(session_id, time_slot_id, status)`。
- 4 个筛查项目建议用 **4 个可空列**而不是 JSON 字段——导出和筛选都简单（医学口径仍待 PRD Q4 确认）。

## 6. 仍然不引入的组件

| 组件 | 不引入的理由 |
| --- | --- |
| **Redis** | 验证码存 MySQL 小表（4.3）；名额并发靠 InnoDB 行锁（5.1）；无高频只读热点。加它等于多一个容器、多一层锁失效的思考成本。 |
| **消息队列** | 发信用 `BackgroundTasks`，定时用 crontab。没有需要削峰的场景。 |
| **微服务** | 三个容器已是合理粒度。再拆只增加部署与排查成本。 |
| **Elasticsearch** | 名单筛选是等值查询，索引足够。 |
| **推送 SDK（极光/个推）** | 通知场景低频，用邮件即可，不引厂商通道。 |
| **K8s / 服务网格** | 单机单副本，用不上。 |
| **独立 Web 管理后台** | PRD 明确不做。后续要做加个静态站即可。 |

## 8. 部署与运维

### 8.1 关键路径：域名备案

国内服务器绑域名对外提供 80/443 必须备案，1–3 周。**第一天就要启动，与开发并行。**

省事路径：向学校网络中心申请已备案的校内子域名（如 `tb.hebau.edu.cn`），可完全跳过备案流程。

### 8.2 部署形态

一台 2C4G 服务器（或学校提供的虚拟机），Ubuntu LTS：

```
docker compose up -d
  ├── caddy      :80/:443   自动 HTTPS
  ├── app        :8000      FastAPI (uvicorn)
  └── mysql      :3306      InnoDB, data volume
```

Alembic 迁移在容器启动前执行一次（`alembic upgrade head`）。

### 8.3 定时任务

**宿主机 crontab 调容器内管理命令**，不起第四个容器：

```
# 每小时：时段结束后置爽约
0 * * * * docker exec app python -m app.jobs.close_slots
```

之所以不用 APScheduler 内嵌：uvicorn 多 worker 会**每个进程都跑一遍**，导致重复执行。单 worker 才安全，但单 worker 又损失并发能力。crontab 没有这个问题。

### 8.4 备份

`mysqldump` 每日导出 + 保留 30 天（保存期限待 PRD Q11）。备份文件同时落本地和另一台机器/对象存储。**单机部署最大风险是磁盘挂掉数据全丢，这步不能省。**

### 8.5 监控

`/health` 接口 + 日志 + 磁盘占用告警，不接 APM。

## 10. 成本量级

| 项 | 说明 |
| --- | --- |
| 服务器 | 1 台 2C4G，千元级/年 |
| 域名 | 几十元/年；用学校子域名则为 0 |
| 备案 | 免费但耗时 1–3 周 |
| HTTPS | Caddy + Let's Encrypt，0 元 |
| 邮件 | 学校 SMTP 通常免费；企业邮/邮件推送有免费额度 |
| 短信（如日后回退） | 按条计费 |

相比 V1 小程序方案：固定成本从 0 变为「服务器 + 域名」年费，运维从 0 变为「需要有人能登服务器看日志」。
相比 V2：**去掉了短信按条成本**，但换来了邮件投递率的不确定性。
