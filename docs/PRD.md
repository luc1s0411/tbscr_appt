# 结核病筛查预约管理 App PRD（V1 / MVP）

- 使用单位：河北农业大学校医院
- 交付形态：Android APK（V1.1 起由「微信小程序」改为 APK，登录方式由短信验证码改为邮箱验证码）
- 版本：V1.1（MVP）
- 日期：2026-10-23
- 说明：本文仅覆盖第一版范围。文中所有 **⚠️待确认** 为尚未定论的项，已标注位置但不自行填充结论；确认前不计入已定需求。

## 1. 项目目标

### 1.1 一句话目标

把校医院结核病筛查的「排期 → 预约 → 到场 → 结果归档」链路统一到一个 App 内完成，替代靠人工登记与表格汇总的管理方式。

### 1.2 分角色目标

| 角色 | 目标 |
| --- | --- |
| 学生 | 用邮箱验证码登录一次，即可看到自己能约的日期与时段，完成预约、查看预约凭证、在截止时间前取消或改约 |
| 校医院管理员 | 按「日期 + 时段 + 人数上限」配置号源；既能按学院批次下发名额，也能放开让学生自助补约；现场扫码核销；录入结果并导出 Excel |
| 校医院管理侧 | 任一时段的「已约 / 已核销 / 未到 / 已取消」可实时查看，数字与名单一致，可导出存档 |

### 1.3 第一版的范围主张

- 只做**预约与到场管理**，不做检测结论的线上发布（结果不在 App 展示）。
- 号源是唯一需要严格控流的对象：所有业务正确性优先保证「不超约、不重复约、名额可回收」。
- 管理端与学生端在**同一个 App** 内，用角色区分能力，不单独开发 Web 后台。

### 1.4 量化目标

⚠️待确认：以下指标需甲方给出当前基线后才可写死，第一版暂不作为验收依据。

- 单个筛查场次的人工统计工时（当前值 / 目标值）
- 预约到检率（当前值 / 目标值）
- 单场可承载人数上限

## 2. 核心用户流程

### 2.1 角色

| 角色 | 说明 |
| --- | --- |
| 学生 | 河北农业大学在校生，邮箱验证码登录 |
| 校医院管理员 | 配置号源、排期、核销、录入结果、导出。⚠️待确认：是否区分「超级管理员 / 现场操作员」两级权限 |

### 2.2 流程 A：管理员配置号源

1. 管理员登录管理端。
2. 创建筛查场次：选择日期、添加时段（例：08:00–08:30）、设置每个时段的人数上限。
3. 场次发布后，号源在学生端可见并可预约。
4. ⚠️待确认：是否需要「一次配置批量生成多天/多时段」的复制能力；时段长度是否固定值。

### 2.3 流程 B：学院批次排期（统一组织路径）

1. 管理员为指定学院（或班级）在某日期、某时段上分配名额。
2. 该学院学生登录后，看到的是本批次可选的日期与时段。
3. 学生选择时段 → 提交 → 生成预约单，状态「已预约」。
4. ⚠️待确认：批次粒度是学院还是班级；学生与学院/班级的对应关系从何而来（学号名册导入 / 学生首次登录自填 / 其他）。
5. ⚠️待确认：已被批次分配的学生，能否改选到自助号源，以及原批次名额如何处理。

### 2.4 流程 C：学生自助预约（补约路径）

1. 学生在号源页按日期浏览，看到各时段剩余名额。
2. 选择时段 → 提交预约。
3. 系统校验：同一学生同一场次不可重复预约；所选时段剩余名额 > 0 时扣减名额并生成预约单。
4. ⚠️待确认：自助预约对「已有批次分配」的学生是否可见/可用（与 2.3-5 为同一决策点）。
5. ⚠️待确认：可提前预约的天数 N（影响「可约未来 N 天」的提示与校验）。

### 2.5 流程 D：预约变更

1. 学生进入「我的预约」，可发起取消或改约。
2. 规则：开检前 24 小时可取消、可改约，不限次数；开检前 24 小时内不可操作。
3. 取消或改约成功后，原时段名额立即回到号源池。
4. 状态流转：`已预约 → 已取消` / `已预约 → 已改约（原单作废） / 已预约 → 已核销` / `已预约 → 爽约（仅记录，不限制后续预约）`。
5. ⚠️待确认：「爽约」是由时段结束后系统自动置位，还是管理员手动标记。
6. ⚠️待确认：「不限次数改约」是否需要对同一时段反复取消再约做频次提示（当前按不限次数实现）。

### 2.6 流程 E：现场核销

1. 学生到场，出示预约码（二维码，含可读的数字编号作为兜底）。
2. 管理员扫码 → 核销成功 → 该预约单状态变为「已核销」。
3. 重复扫码时提示「已核销」，不重复计数。
4. 管理端实时查看某时段的已核销数、剩余未到人数、未到名单。
5. ⚠️待确认：现场设备形态（管理员用自己手机 / 校医院固定设备）；弱网或无网时是否允许手动输入编号核销。

### 2.7 流程 F：结果录入与归档

1. 本次筛查含 4 个项目：症状筛查问卷、PPD 皮试、胸片/DR、抽血（IGRA）。
2. 管理员按预约单录入各项目的结果状态。
3. ⚠️待确认：结果状态的字段与枚举值需由校医院给出医学口径，本文不自拟「阴性/阳性」等结论词。
4. ⚠️待确认：因 PPD 需注射后 48–72 小时才能判读、且第一版不做二次到院预约，结果录入必然是**首诊之后的异步补录**。是否允许跨多天、多次补录同一预约单，需确认。
5. ⚠️待确认：症状筛查问卷是现场纸质填写后由医生录入，还是学生线上填写（线上填写未列入第一版，见第 4 节）。
6. 录入完成后按条件导出 Excel（场次/日期/学院/状态），用于存档或对外报送。

### 2.8 流程 G：学生查看结果

- 第一版**不在 App 展示任何检测结果**（含结论档位与报告）。
- ⚠️待确认：学生端是否至少显示「已完成检测 / 待出结果」这类进度状态。若确认完全不显示，则学生端不设结果相关页面。

## 5. 验收标准

验收以「可复现的操作 + 可核对的数字」为准。以下每条均需在测试环境实际跑通。

### 5.1 登录与身份

1. 新邮箱输入正确验证码后可完成登录并进入身份绑定页；错误或过期验证码被拒绝并给出提示。
2. 同一邮箱重新登录不产生第二个账号。
3. 未完成身份绑定的账号无法提交预约。

> 附加校验（不对应独立编号，避免打乱后续条款序号）：同一邮箱 60 秒内重复请求验证码被拒绝；验证码使用后立即失效；同一账号连续输错超过上限需冷却。

### 5.2 号源与并发

4. 管理员将某时段上限设为 X 后，学生端该时段剩余名额显示为 X。
5. 该时段被约满后，第 X+1 次提交被拒绝，提示名额已满，且不产生预约单、不出现负余量。
6. 同一学生对同一场次重复提交预约，第二次被拒绝。
7. 并发提交（同一时段多请求同时到达）后，已约人数不超过上限。

### 5.3 批次与自助预约

8. 被分配某学院批次的学生，登录后看到的可约时段与该批次配置一致。
9. 不属于该批次的学生，无法预约该批次专属号源（⚠️待确认是否允许跨批次抢占剩余名额；确认前按不可跨批次验收）。

### 5.4 变更规则

10. 距开检时间 > 24 小时，取消成功，状态变为「已取消」，该时段剩余名额 +1。
11. 距开检时间 ≤ 24 小时，取消与改约均被拒绝并提示原因。
12. 改约成功后原预约单作废、原名额回收，新时段名额 -1。

### 5.5 现场核销

13. 扫码核销后状态变为「已核销」，该时段已核销数 +1。
14. 同一预约码重复扫码，提示已核销，已核销数不重复累加。
15. 未到、已取消的预约单无法被核销。

### 5.6 统计与导出

16. 任一时段的「已约 / 已核销 / 未到 / 已取消」数量与名单条数逐一对应，合计等于该时段预约单总数。
17. 导出的 Excel 行数与筛选结果条数一致，字段与页面展示字段一致，4 个筛查项目的结果列均存在。

### 5.7 结果可见性

18. 学生端全流程任何页面均不出现检测结果内容（若确认保留进度状态，则仅出现「已完成检测 / 待出结果」，不含结论）。
19. 管理员在录入结果前，导出文件中结果列为空，不出现默认值。
